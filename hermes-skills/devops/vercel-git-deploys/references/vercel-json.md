# vercel.json — git configuration

All options also available programmatically via `vercel.ts` exporting a `VercelConfig`.

## `git.deploymentEnabled`

Type: object of branch identifier → boolean, **or** boolean. Default `true`.

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "git": { "deploymentEnabled": { "dev": false } }
}
```

Minimatch globs:

```json
{ "git": { "deploymentEnabled": { "internal-*": false } } }
```

**Multiple matches resolve permissively.** If a branch matches several rules and at least one is `true`, it deploys:

```json
{ "git": { "deploymentEnabled": { "experiment-*": false, "*-dev": true } } }
```

Branch `experiment-my-branch-dev` **does** deploy.

Disable everything:

```json
{ "git": { "deploymentEnabled": false } }
```

## `github.autoJobCancelation`

Boolean. GitHub only. Set `false` to build every push in sequence rather than cancelling superseded builds on the same branch.

```json
{ "github": { "autoJobCancelation": false } }
```

## `github.autoAlias`

Boolean. Set `false` to create preview deployments on merge instead of production. The docs carry an explicit warning to use the staged production build workflow instead — see `promotion-and-rollback.md`.

## Deprecated

### `github.silent`

Replaced by per-project toggles in Settings → Git → Connected Git Repository. If it was previously set, Vercel migrates the setting automatically.

### `github.enabled`

Replaced by `git.deploymentEnabled`. Still worth knowing about: **`github.enabled: false` also blocks deploy hooks**, which is a documented behaviour of the old flag.

## Other keys referenced elsewhere in this skill

- `framework`, `buildCommand`, `outputDirectory`, `devCommand` — per-deployment overrides of the dashboard Build and Deployment settings
- `relatedProjects: ["prj_..."]` — max 3, same repository only, no CLI support
- `headers` — applies to every static response; a common home for security headers when a project has no framework

## Security headers as a `headers` block

Useful when reconstructing or auditing a static project's configuration:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "headers": [
    {
      "source": "/(.*)",
      "headers": [
        { "key": "X-Frame-Options", "value": "DENY" },
        { "key": "X-Content-Type-Options", "value": "nosniff" },
        { "key": "Referrer-Policy", "value": "strict-origin-when-cross-origin" },
        { "key": "Strict-Transport-Security", "value": "max-age=63072000; includeSubDomains; preload" }
      ]
    }
  ]
}
```

Headers present on a `200` static response but absent from a `401` generated by middleware tell you which layer set them — `vercel.json` headers apply to static responses, middleware sets its own.

## Deploy hooks

Created at Project → Settings → Git → **Deploy Hooks**. Requires the project to be connected to a repository. Pick a name and a branch; you get a URL.

```bash
curl -X POST https://api.vercel.com/v1/integrations/deploy/<projectId>/<hookId>
```

- Accepts GET or POST. No authentication header, no payload — **the URL is the credential.** Treat it like a password; revoke and recreate if leaked.
- Build cache is on by default. Opt out with `?buildCache=false`. Hooks created before 11 May 2021 have it off by default — append `?buildCache=true` or recreate the hook.
- Repeated requests for the same version cancel previous deployments from the same hook.
- Limits: 5 per project on Hobby and Pro, 10 on Enterprise.
- Blocked entirely by the legacy `github.enabled: false`.
- One hook per branch unless you have multiple data sources. Name them so you can tell which one fired.

## Git LFS

Enable at Project → Settings → Git. **You must redeploy after turning it on.** A committed LFS pointer file that was never resolved is a classic cause of a served file being a few hundred bytes instead of megabytes.

## Require Verified Commits

Project → Settings → Git. **GitHub only.** Unverified commits are automatically canceled. Tool-authored commits are frequently unverified.
